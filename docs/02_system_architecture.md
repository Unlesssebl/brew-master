# Архитектура системы: Brew Master (Beer Empire)

## 1. Концепция и Паттерны
Проект построен на изолированной микросервисной архитектуре.
Связь между сервисами осуществляется **исключительно через PostgreSQL** (используется как единый источник истины и брокер сообщений). Сторонние брокеры (Kafka, RabbitMQ) намеренно не используются для минимизации инфраструктурного оверхеда.

## 2. Компоненты системы

### A. Telegram Gateway (Клиент и Контроллер)
- **Роль:** Продвинутый визуальный клиент (Живая Таверна) и шлюз.
- **Инфраструктура:** Используется локальный `telegram-bot-api` сервер (поднят в Docker) для обхода ограничения в 30 сообщений/сек и устранения задержек сети до серверов Telegram. Транспорт: Webhook (не Polling).
- **Паттерн Debouncing:** В высоконагруженных механиках (Аукцион, Рейды) клики изменяют только In-Memory стейт в **Redis**. Фоновый воркер делает `editMessageText` 1 раз в секунду, чтобы избежать ошибки `429 Too Many Requests`.
- **State Management:** Отказ от передачи данных в `callback_data` (лимит 64 байта). Кнопки шлют только короткий Action ID. Полный JSON-состояния лежит в Redis: `session:{chat_id}:{message_id}`.

### B. Game Engine (Игровое ядро)
- **Роль:** Основной обработчик синхронной бизнес-логики.
- **Задачи:** Расчет формул (крафт, диверсии), проверки инвентаря, валидация бизнес-правил.
- **Взаимодействие с БД:** Строго транзакционное с использованием пессимистичных блокировок (`FOR UPDATE`). Ядро отвечает за консистентность баланса.

### C. Economy & Async Worker
- **Роль:** Фоновый процессор длительных и периодических операций.
- **Задачи:**
  - Начисление оффлайн-производства (лимит 24ч).
  - Списание налогов и выплата патентов.
  - Агрегация продаж для расчета Market Saturation ($D_{penalty}$).
  - Управление таймерами экспедиций и порчи пива (72ч).

### D. LLM Game Master (Агент-генератор)
- **Роль:** Генерация нарратива и динамических событий.
- **Интеграция:** Изолированный микросервис. Читает стейт мира, отправляет запрос к API (Gemini), парсит ответ через Pydantic-схемы.
- **Ограничения:** Не имеет прямого доступа к изменению состояния БД (только чтение). Сгенерированные JSON-события кладутся в очередь, после чего `Game Engine` применяет числовые эффекты.

## 3. Механизм очередей (PostgreSQL IPC)
Асинхронные задачи передаются через выделенную схему `queue`. Воркеры (Python) забирают задачи, используя конструкцию:
```sql
FOR UPDATE SKIP LOCKED
```
Это позволяет безопасно масштабировать количество параллельных обработчиков (воркеров) без риска дублирования задач или дэдлоков.
