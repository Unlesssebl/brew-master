\# Архитектура проекта: Beer Empire

\#\# 1\. Концепция и Паттерны  
Проект построен на изолированной микросервисной архитектуре.   
Связь между сервисами осуществляется исключительно через PostgreSQL (используется как единый источник истины и брокер сообщений). Сторонние брокеры (Kafka, RabbitMQ) намеренно не используются для минимизации инфраструктурного оверхеда.

\#\# 2\. Компоненты системы

\#\#\# A. Telegram API Gateway (Бот-клиент)  
* **Роль:** Продвинутый визуальный клиент (Живая Таверна).  
* **Задачи:** Рендеринг 2D-матриц эмодзи, обработка D-pad навигации, форматирование Rich Messages (API 10.1+) для таблиц рынка и использование стилизованных кнопок (API 9.4+).  
* **Интерфейс:** Построен по паттерну «SPA Dashboard» внутри чата. Используются микро-обновления через Toast (`answerCallbackQuery`), чтобы избегать перерисовки всего экрана.
* **State Management:** Отказ от передачи данных в `callback_data` из-за лимита в 64 байта. Используется паттерн Redis Message-Bound State (`session:{chat_id}:{message_id}`), где кнопки шлют только короткий Action ID.
* **Инфраструктура:** Используется локальный `telegram-bot-api` сервер (поднят в Docker) для обхода ограничения в 30 сообщений/сек и устранения задержек при анимациях (QTE).

\#\#\# B. Game Engine (Игровое ядро)  
\* \*\*Роль:\*\* Основной обработчик синхронной логики.  
\* \*\*Задачи:\*\* Расчет статов крафта при варке, проведение проверок PVP (шпионаж/диверсии), обновление инвентаря.  
\* \*\*Взаимодействие с БД:\*\* Использует пессимистичные блокировки (\`SELECT ... FOR UPDATE\`) для всех транзакций изменения баланса и ресурсов.

\#\#\# C. Economy & Async Worker  
\* \*\*Роль:\*\* Фоновый процессор экономики и торговых операций.  
\* \*\*Задачи:\*\* \* Агрегация транзакций из логов и выплата роялти владельцам патентов (раз в час).  
    \* Списание налогов за удержание патентов.  
    \* Расчет рыночного перенасыщения (Market Saturation) и обновление множителей спроса.

\#\#\# D. LLM Game Master (Агент-генератор)  
\* \*\*Роль:\*\* Генерация нарратива и случайных событий.  
\* \*\*Задачи:\*\* Чтение состояния мира, генерация JSON-событий через LLM, строгая Pydantic-валидация ответа, запись готовых событий в очередь бота для отправки игрокам.  
\* \*\*Ограничения:\*\* Не имеет прямого доступа к изменению состояния БД (только чтение). Все изменения проходят валидацию через Game Engine.

\#\# 3\. Механизм очередей (PostgreSQL IPC)  
Асинхронные задачи (генерация событий, выплата роялти) передаются через схему \`queue\`. Воркеры (Python) забирают задачи используя конструкцию \`FOR UPDATE SKIP LOCKED\`, что позволяет безопасно масштабировать количество параллельных обработчиков без риска дублирования задач.
