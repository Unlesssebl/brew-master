# TDD: Нативные механики Telegram API («Живая Таверна»)

Данный документ является **техническим справочником** по реализации игровых механик в Telegram API 10.1+. Игровой баланс, лор и статусы готовности механик описаны в Game Design Document: [01_gdd.md](file:///f:/Work/Projects/brew-master/docs/01_gdd.md).

## 1. Базовые Технические Паттерны

### 1.1. Система очередей (Debouncing Pattern)
Главная проблема любых "живых" механик в Telegram — жесткий лимит Flood Control при обновлении сообщений (не более ~30 `editMessageText` в секунду на бота, и строгие лимиты на конкретный чат).
**Техническое решение:**
- Клиентские действия (нажатия `CallbackQuery`) мгновенно обновляют состояние в **In-Memory хранилище (Redis)**.
- Сервер отвечает `answerCallbackQuery` (быстрый toast без изменения сообщения), чтобы убрать "часики" с кнопки.
- Фоновый асинхронный воркер проверяет стейт 1 раз в секунду и делает ровно один `editMessageText` с актуальными данными.
*Связанные механики в GDD:* Социальные рейды, Аукцион, Терпение пивовара.

### 1.2. Бросок кубиков (`sendDice`)
Позволяет делегировать тяжелые анимации аппаратному ускорению Telegram клиента.
**Техническое решение:**
- Бот вызывает метод `sendDice(emoji="🎰")`.
- Telegram API немедленно возвращает в объекте `Message` итоговое значение (для слотов `dice.value` от 1 до 64).
- Бэкенд делает `asyncio.sleep` на время проигрывания анимации в клиенте (около 2-3 секунд), после чего отправляет сообщение с результатом.
*Связанные механики в GDD:* Подпольное казино, RPG-Крафт.

### 1.3. Стилизованные Inline-кнопки
Официально Telegram не позволяет менять цвет Inline-кнопок, но существует недокументированный хак или обертка над Web App для придания кнопкам стилей `primary` (синий) и `danger` (красный).
**Техническое решение:**
- Использование ключа `style` в `InlineKeyboardButton` или использование нативных Keyboard Button API 10+. Применяется для акцентирования внимания в условиях дефицита времени.
*Связанные механики в GDD:* Социальные рейды, RPG-Крафт.

### 1.4. Разделенный интерфейс (Multi-message Layout)
Для создания ощущения "движка" игра отказывается от обновления одного гигантского сообщения.
**Техническое решение:**
- Отправляются два сообщения. Верхнее (`msg_engine`) закрепляется в чате через `pin_chat_message` и содержит карту или сетку кнопок.
- Нижнее сообщение (`msg_log`) служит текстовым логом.
- Нажатия на кнопки верхнего сообщения вызывают `editMessageText` **только** для нижнего сообщения. Это экономит трафик и убирает визуальное "прыгание" интерфейса.
*Связанные механики в GDD:* Аукцион, Навигация по складу, Рейды.

### 1.5. Скрытый лор (Blockquote Expandable)
Упаковка больших текстов от LLM.
**Техническое решение:**
- Использование HTML Parse Mode с новым тегом `<blockquote expandable>Текст</blockquote>`. Текст автоматически сворачивается в плашку клиентом Telegram, экономя место на экране.
*Связанные механики в GDD:* Экспедиции, Рецензии от LLM.

### 1.6. Экранные эффекты (Haptic Feedback)
Использование визуальных и тактильных эффектов при важных событиях.
**Техническое решение:**
- Передача параметра `message_effect_id` (например, ID эффекта "Праздник" или "Огонь") при вызове `sendMessage`. Клиент Android/iOS реагирует на это вибрацией (Haptic) и полноэкранной анимацией поверх чата.
*Связанные механики в GDD:* Выпадение легендарных рецептов, Казино.

### 1.7. Глобальный Inline-режим
Взаимодействие вне бота.
**Техническое решение:**
- Бот регистрирует `@dp.inline_query()`. При вводе `@bot_name sell 100` генерируется `InlineQueryResultArticle`.
- Когда другой игрок жмет кнопку "Купить" на этой статье, бот получает Callback с `inline_message_id` и обновляет карточку, параллельно проводя транзакцию в БД.
*Связанные механики в GDD:* Черный рынок.

### 1.8. Псевдографика (Матрица Эмодзи)
Создание графики из текста.
**Техническое решение:**
- Генерация строки текста из массивов 5x5. Для оптимизации используются короткие коды эмодзи или кастомные стикерпаки Telegram Premium. Перерисовка идет через `editMessageText` (ограничено Debouncing-паттерном).
*Связанные механики в GDD:* Барная стойка (Tapper), Навигация по складу.

## 2. Архитектура Бэкенда

Для поддержки высоконагруженных механик (типа рейдов) архитектура должна соответствовать следующим критериям:

1. **Local Bot API Server:** Чтобы минимизировать сетевой пинг до серверов Telegram, бот должен общаться с локальным `telegram-bot-api` инстансом.
2. **Webhook Transport:** Polling не подходит для Production из-за задержек. Все апдейты должны прилетать на ASGI/FastAPI сервер через Webhook.
3. **Redis Bound State:** Все `callback_data` должны быть короткими (хранить только идентификатор действия `action_id`). Контекст сессии, состояние котла и данные рейдов должны лежать исключительно в in-memory БД (Redis) для скорости доступа O(1).
